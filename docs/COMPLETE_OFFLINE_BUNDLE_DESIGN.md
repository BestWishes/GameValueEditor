# 完整离线包工具设计（本地实施）

发布状态：本能力纳入 v0.5.0，见[集成复核与发布记录](RELEASE_0_5_0_INTEGRATION_REVIEW.md)。下文“本地、不提交、不发布”和 0.4.9 产物信息是原实施轮次的历史边界，不代表后续用户授权的发布状态；完整离线 ZIP 始终只供本地/QQ 分发。

后续增强见 [LOCAL_RELIABILITY_DESIGN.md](LOCAL_RELIABILITY_DESIGN.md)：外部核验记录、完整性与新旧分离、实际模块/页面核验及标准打包失败保护。下文保留原轮次的设计和 70 项检查历史，不代表增强后的最新断言数量。

## 目标与边界

本轮只修复离线打包能力，不提交、不推送、不打标签、不上传、不清理远端资产。主程序维持 0.4.9，模块版本、Host API、目录协议与游戏构建指纹不改。已有标准 ZIP 和已交付的完整离线 ZIP 均保留。

离线包不是另一份主程序发布版本：它组合已经验证的标准主程序 ZIP 和模块目录中与该宿主兼容的模块 ZIP，供本地/QQ 分发。模块安装布局必须与应用的便携式加载器一致，不能仅把模块 ZIP 放在 EXE 旁边。

## 已确认的问题

1. 全局技能脚本还使用旧目录协议/API，最新离线包依靠临时修正脚本生成。
2. 仓库旧入口 `create-local-complete-package.ps1` 默认 0.4.3，从可变的 `artifacts/package` 复制；缺少主程序版本、完整模块兼容和内容验证，还会隐式下载。
3. 两个入口存在重复实现，固定暂存目录和提前删除旧输出使重试不安全。
4. `publish.ps1` 的通配清理会误删本地完整离线 ZIP。

## 输入和单一实现

- 仓库新增正式入口 `scripts/build-complete-offline-bundle.ps1`，共享实现放在 `scripts/offline-bundle.ps1`。
- 原仓库命令和全局技能命令保留参数兼容，均转交正式入口，不再独立组包。
- 省略版本时读取宿主项目版本；省略模块仓库时使用相邻的 `GameValueEditor-Modules`。
- 主程序必须来自 `dist/GameValueEditor-v{version}-win-x64.zip`，不从构建暂存目录复制。
- 标准 ZIP 的大小、SHA-256、源码提交与能力声明对照本地发布索引；未进入索引的已验证标准 ZIP 可显式传入 `ExpectedHostSha256`。索引已经存在的记录不允许用该参数绕过。
- 主程序和更新器的 ProductVersion 必须对应指定版本和同一源码提交。
- 工具理解目录 Schema 5（使用模块仓库的本地 JSON Schema 严格校验）；宿主声明上限必须至少支持该 Schema。未来未知 Schema 明确拒绝，不猜测、不自动放宽。
- 按模块 API 和宿主最小/最大版本，自动选择每个模块保留快照中版本最高的兼容项；不要求两种版本号相等。默认包含目录内所有模块，可显式用 `ModuleIds` 选择子集，未知/重复 ID 或没有兼容版本均报错，不静默漏装。
- 只读取本地 `dist` 中的模块 ZIP：校验大小和哈希，缺少时说明文件名，不隐式联网。

## 包内容与兼容校验

- 标准 ZIP 必须恰含六个根文件：应用、更新器、README、LICENSE、SECURITY、release-compatibility.json，不允许任何用户数据。
- 模块 ZIP 必须恰含 `module.json` 和其声明的根 DLL；校验 JSON Schema、ID、版本、API、宿主范围、进程名、编辑器描述、完整构建指纹及未知构建验证声明与所选目录快照一致。
- ZIP 入口统一检查：拒绝重复（含大小写碰撞）、目录入口、路径跳转、绝对路径、NTFS ADS、符号链接、超限内容。只将允许的入口写入新建目录。
- 包内保留标准文件及模块文件原始字节；新建 `data/modules/installed.json`（Schema 1，仅 Id/Version/InstalledUtc）与中文使用说明。不读用户游戏库、图标、存档、缓存或更新事务。
- 输出验证反向检查全部入口、逐文件 SHA-256 和安装清单，既能检查新包，也能检查已有包。

## 失败安全和重试

- 每次使用唯一、仓库内的暂存目录；输出仅允许在宿主 `dist` 内，检查路径分隔边界和重解析点，不清空已有目录。
- 临时 ZIP 与目标位于同一目录，验证内容和隔离启动成功后才提升为目标文件；失败不删除/替换原包。
- 内容一致的已有包默认复用，仍验证内容和启动；不同内容默认拒绝覆盖，显式 `Force` 才可在新包完全验证后原子替换。
- `VerifyOnly` 只验证已有包；不改包、不构建、不联网。启动验证在唯一隔离目录中进行，只终止自己启动的进程，不触碰当前应用用户数据。
- 源文件读取期间锁定为只读共享；完成前复核源哈希，避免目录/文件中途变化造成混合包。
- 子集使用 `selected-offline` 名称，避免把部分模块包误称为完整包；拒绝使用标准主程序包文件名作为输出。
- 标准发布清理只匹配标准 ZIP 的精确命名格式，保留完整/子集离线包。

## 测试与文档

新增无需 Pester 的隔离脚本测试：正常目录/API、兼容快照选择、显式子集、坏哈希/大小、缺包、重复身份、目录/清单不一致、ZIP 路径安全、输出路径安全、失败保留原包、复用和显式覆盖。小型合成 fixture 的二进制版本和启动使用测试进程内部替身，不提供生产跳过检查参数。

真实端到端测试使用现有 0.4.9 标准包及三个本地模块，验证真实 ProductVersion、全部文件字节、实际应用隔离启动；生成到独立验证输出，不覆盖已交付包。再次调用默认入口验证复用，检查两个兼容入口。

`verify-release.ps1` 接入工具回归测试。README、RELEASE、ARCHITECTURE 和发布技能同步单一入口、约束、使用方法及验收记录。本轮不执行正式发布脚本。

## 实施前检查（三遍）

1. **方向与需求**：离线组合无需新应用版本；主程序/模块版本独立，兼容依赖 API/版本边界；只做本地交付，无自动更新/回退和远端操作。通过。
2. **安全与失败路径**：核对 ZIP/目录边界、无用户数据、校验早于替换、隔离启动、无隐式下载；已有交付物不作为试验覆盖对象。通过。
3. **入口与长期维护**：确认旧仓库入口确实被 README 引用，保留包装转发；全局技能消除重复逻辑；回归进入正式验证链；标准清理不再误伤离线包。通过。
