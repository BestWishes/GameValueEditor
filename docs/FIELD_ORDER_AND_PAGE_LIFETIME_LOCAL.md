## 详细方案

### 1. 保存字段入口的读写顺序

- 只协调保存字段/快捷入口的 `RefreshSavedValuesAsync`、`WriteSelectedFieldAsync` 和周期锁定，不将不同字段或不同游戏串成全局队列，不修改模块自有页面的读写契约。
- 每个 SavedField 实例有一个非持久化操作状态，由弱引用表管理，不写入资料格式。前台刷新/手改通过显式任务尾链按请求顺序执行，异常也在 finally 中释放下一项；不用阻塞 UI 的同步等待，也不依赖信号量未承诺的公平性。
- 手改提交请求时立即递增读取代并登记待写，旧读取和锁定在后续调用/成功或错误回调中核对代数。新请求在原读取尚未返回时也会使旧显示失效。手动写入串行到实际结果和持久化收尾完成，较早写入不可能晚于较新写入完成后回填旧目标。
- 周期锁定只尝试取得空闲字段，忙字段跳过并按原 750 ms 周期再检查；读取返回后再次核对待写、读取代、取消、目标、锁定和原版本成员。已进入同步写入不能撤销，手改会等它完成再开始自己的写入。
- 排队/返回时核对原游戏操作及字段仍在原版本；模块字段另核对原适配器实例。删除、切换游戏/版本、断开、关闭或模块停用后尚未开始的旧调用拒绝执行；失效结果不覆盖新界面。显式解锁或改变目标不被手改结果重新启用/覆盖。现有四种原生写入反馈、模块语义结果、错误与保存规则保留，不新增自动回退或写入重试。
- 整批刷新记录因后续操作被跳过的情况，不用旧“已刷新”提示覆盖较新的手改反馈。

### 2. 宿主绑定模块页面有效期

- 主程序为每个 API 6+ 页面创建一个内部宿主服务包装，捕获页面 Token、当前适配器、进程和构建，并在其所属 Dispatcher 上核验。页面失效/主程序关闭后 `ShowError`、`ReportStatus` 直接丢弃。
- 输入和保存请求在排队执行前及异步返回后检查有效期；旧请求抛出取消，不把结果交给旧页面继续使用。WPF 保存字段弹框另捕获原游戏操作，弹框返回后在保存入口前核验，避免期间连接/版本变化时把请求保存到新条目；页面有效期验证器还传入内部保存入口，在语义读取返回、加入资料之前再次核验，不能只在保存全部结束后检查。公共三参数保存字段方法保持原调用方式。
- 不修改公共 SDK、不要求现有三个模块重新打包。即使旧模块仍调用全局错误入口，收到的已是绑定页面的包装，过期回调不会进入真实弹框。
- 模块仍负责自己的页面布局、同步调用和数据验证；不声称可以撤销已经执行的模块或保存操作。

### 3. 保存字段刷新身份核验

- 打开进程读取器后、开始字段读取前核对 PID 和启动时间，沿用 `EnsureInstance`。不匹配明确失败，不能显示“可用”。
- 正常原生/模块刷新、不可读字段的既有提示保留；不扩大读取范围或改游戏内存保护。

## 写代码前三遍检查（完成）

1. **方向与范围**：对照五个确定性复现及现有 SDK/page 契约，明确修复保存字段链和宿主回调，而不是重做模块 UI。宿主包装能保护当前不可变模块包，不需要发布新模块或升级 API。
2. **顺序与失败边界**：逐项跟踪写请求登记、前项完成、结果/保存、字段删除、显式解锁、切换/关闭以及模块弹框返回。锁定不排队等待忙字段；所有前台队列释放在 finally，已有同步写入只能等完成；有效期检查必须在 Dispatcher 回调内，不只在排队前检查。
3. **测试与兼容**：复用原样例适配器的测试回调，不向冒烟程序集新增可被模块扫描识别的 IGameAdapter 导出。页面工厂测试采用运行时代理而不是静态插件类。新增顺序/错误释放/不同字段/取消、正常与过期页面请求、队列中的过期回调，以及真实自有内存的正确/过期进程身份回归；先分别在旧逻辑下失败，再修实现，并保留原完整回归。
