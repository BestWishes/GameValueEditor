# Host API 6：模块自有页面与十进制发布版本设计

状态：设计已通过三轮评审，允许进入实现。

主程序 v0.5.1 起正式提供 Host API 8，见[集成发布复核](RELEASE_0_5_1_INTEGRATION_REVIEW.md)及[实际字段协调方案](SHARED_FIELD_COORDINATION_LOCAL.md)：模块继续自主布局，字段写入及整页快照经宿主桥接；旧 API 6/7 页面包保留加载，但未接入协调的模块字段锁定暂停。以下 API 6 设计和当时验收保持历史原貌，不表示当前 SDK 仍停留在 API 6/7。

## 目标

这次改动同时解决两个彼此独立的问题：

1. 主程序与每个游戏模块分别维护自己的发布版本；每次正式发布只前进一个最小刻度。
2. 游戏专属页面的布局、交互和页面状态由模块自己实现；主程序不再用固定页面类型决定模块能做什么。

它们只在发布校验处相遇：使用新页面协议会提升 Host API，但 Host API 是整数协议号，不参与发布版本进位。

## 版本规则

### 正式发布版本

发布版本固定为 `A.B.C`，其中：

- `A` 是非负整数；
- `B`、`C` 只能是 `0` 到 `9`；
- 不接受预览后缀、四段版本、前导零或构建元数据；
- 下一版本等价于把 `A.B.C` 看作三位十进制计数器加一。

因此：

- `0.4.8 -> 0.4.9`
- `0.4.9 -> 0.5.0`
- `0.9.9 -> 1.0.0`
- `2.1.0 -> 2.1.1`

“更新一次”定义为对外发布一次不可变的正式 Release，不是提交一次代码。主程序和各模块分别从自己的最新正式标签计算下一版本，互不跟随：主程序发版不会要求所有模块升版，一个模块发版也不会改变其他模块或主程序的版本。

### 不使用此规则的编号

以下数字表达兼容协议或数据结构，不是发布版本：

- `ModuleHostApi.CurrentVersion`
- `catalog.schemaVersion`
- 本地数据文件的 schema 号
- CLR `AssemblyVersion`

这些编号只在契约不兼容或结构变化时按整数提升。本次模块自有页面新增 Host API 6；SDK 包自身的产品版本仍按发布版本规则从 `4.0.0` 到 `4.0.1`。

### 执行与拦截

- C# 的 `SemanticVersion` 只接受规范版本，并提供唯一的 `Next()` 结果。
- 主程序发布脚本从主程序正式标签计算下一版本，并核对项目版本、更新器版本和打包参数。
- 模块发布脚本按游戏目录读取 `{game}-vA.B.C` 标签，只核对当前模块自己的下一版本。
- Schema 和仓库验证脚本拒绝 `1.2.10`、`01.2.3`、预览版本及跳号。
- 已存在的当前标签只允许走只读复核/中断恢复流程；新发布不得覆盖同名资产。

## 页面职责边界

### 模块拥有

模块负责：

- 页面中的全部 WPF 视觉树，可以使用 XAML、`UserControl` 或纯代码构建；
- 页面自己的 ViewModel、筛选、选择、分组、按钮、提示文字和交互流程；
- 调用本模块适配器的读取、写入、刷新和游戏保存逻辑；
- 页面级异步状态以及页面销毁时的取消和事件解绑；
- 编辑器稳定 ID、显示名称、排序、说明和会话生命周期声明。

模块不再登记 `Inventory`、`CharacterAttributes`、`Entity` 等页面角色。新协议中不存在根据 `Kind` 或 `Role` 选择宿主模板的分支。

### 主程序拥有

主程序只负责：

- 左侧游戏内功能导航和右侧页面容器；
- 应用主题资源以及一组稳定、可选使用的资源键；
- 当前进程、构建身份和页面生命周期令牌；
- 通用输入弹框、错误弹框、底部状态文本和“添加到已保存字段”流程；
- 模块安装、完整性校验、加载隔离、兼容性诊断和卸载；
- 旧 Host API 2 到 5 模块的兼容渲染。

宿主不得读取模块页面内部控件、依赖其 ViewModel 类型，或根据编辑器 ID 猜测页面形态。

## Host API 6 契约

SDK 新增以下概念：

- `GameEditorKind.Custom`：只用于满足旧 `IGameAdapter.Editors` ABI；API 6 不读取它来生成页面。
- `GameEditorPageContext`：包含当前 `GameProcessContext`、`GameBuildIdentity`、宿主服务和页面生命周期 `CancellationToken`。
- `IGameEditorHostServices`：提供值输入、保存语义字段、状态报告和错误显示；不暴露 `MainWindow`、`MainViewModel` 或数据库实现。
- `IGameEditorPage`：持有模块创建的 `FrameworkElement`，并负责 `Dispose()`。
- `IGameEditorPageFactoryProvider`：按稳定编辑器 ID 创建页面。

API 6 模块仍实现 `IGameAdapter`，因此既有语义字段读取、写入、构建识别和兼容性诊断保持不变。模块清单的 `editors` 只保留 `id`、`displayName`、`order`、`sessionOnly`，不再包含 `kind`。

## 页面生命周期

1. 宿主连接到已识别构建并选中适配器。
2. 宿主为每个编辑器创建独立的生命周期令牌和 `GameEditorPageContext`。
3. 模块工厂返回 `IGameEditorPage`；其 `View` 被放入通用 `ContentPresenter`。
4. 页面自行在首次 `Loaded` 时读取游戏数据；切换标签不要求重建页面。
5. 断开游戏、切换适配器、更新/卸载模块或退出程序时，宿主先取消令牌，再从视觉树移除页面，最后调用 `Dispose()`。
6. API 2 到 5 的无 UI 模块继续使用 collectible `AssemblyLoadContext`。WPF 会缓存页面类型/资源，API 6 UI 模块因此使用进程期非回收的独立加载上下文；页面引用仍会释放，安装源包可立即删除，影子副本在主程序退出后的下次启动清理。

页面不得订阅无法在 `Dispose()` 中解除的静态事件，不得把宿主服务、页面或游戏对象存入静态字段。模块仍须每次操作重新定位实时游戏对象，不能跨会话保存地址。

2026-10-07 本地工作树补充（未提交、未发布）：宿主为每页内部包装 `IGameEditorHostServices`，在 Dispatcher 实际执行状态/错误回调时核对页面 Token 和原适配器/进程/构建。旧页面服务失效后不得打开新弹框或回填状态；输入/保存请求开始和返回后取消，保存弹框返回和语义字段读取返回还在资料新增前核验。模块自己的取消/Dispose 职责不变，公共 SDK 和 API 编号不变，现有模块包无需重构建。执行方案与回归见[字段顺序和页面有效期](FIELD_ORDER_AND_PAGE_LIFETIME_LOCAL.md)。

## WPF 与主题

SDK 改为 `net8.0-windows` 并启用 WPF，因此模块可以在自己的程序集内编译 XAML/BAML。WPF 框架程序集和唯一一份 `GameValueEditor.ModuleSdk` 由默认加载上下文共享；模块 DLL 与嵌入资源从 API 6 专用影子加载上下文加载。由于 WPF 内部会缓存已创建的页面类型和资源，不能诚实承诺该上下文可在进程内完全回收；宿主保证释放页面和安装源包文件锁，影子副本延迟到退出后清理。

页面默认继承宿主字体和前景色。模块可通过 `DynamicResource` 使用稳定资源键，例如 `WindowBrush`、`PanelBrush`、`BorderBrush`、`MutedTextBrush`、`AccentBrush`。模块不能复制宿主程序集或依赖宿主内部样式类；找不到可选资源键时必须仍能使用系统默认样式显示。

发布包继续只含模块 DLL 和 `module.json`。XAML、图标等编译资源应嵌入模块 DLL；若以后需要外部资源，必须另行提升包 Schema，不能在 API 6 中暗中放宽文件白名单。

## 兼容与迁移

- Host API 2/3：继续根据旧能力接口推导旧页面。
- Host API 4/5：继续读取 `IGameEditorPageProvider` 的角色登记并使用旧模板。
- Host API 6：必须实现 `IGameEditorPageFactoryProvider`；宿主拒绝缺页、重复页、返回 `null`、页面 ID 不一致或工厂异常。
- 三个官方模块本次全部迁移到 API 6，由各自程序集提供页面；旧模板只为第三方旧包保留。
- 已保存字段继续使用原有模块 ID 和语义字段键，不迁移地址，不改变锁定与 `SessionOnly` 策略。

## 失败隔离

- 单个页面创建失败时，该模块加载失败并给出可读原因，不允许留下半数可用、半数未知的页面集合。
- 页面读取/写入异常由页面交给宿主公共错误入口；宿主程序不得崩溃。
- 生命周期令牌取消后不再更新 UI。
- 未识别构建仍在 `Supports` 或页面能力检查处安全失败，绝不因页面迁移放宽构建匹配。
- 宿主保存快捷字段时仍调用模块 `ReadField` 获取权威当前值，页面不能伪造持久化结果。

## 验证矩阵

- 版本：普通递增、补位、跨主位、非法两位小段、跳号、主程序/模块相互独立。
- 契约：API 6 清单无 `kind`，每个编辑器恰有一个模块页面，页面程序集属于模块。
- UI：三种主题、标签切换、筛选、单项/批量修改、保存字段、错误显示。
- 生命周期：断开、切换游戏、模块重载、卸载、退出；页面取消并释放，影子目录可删除。
- 兼容：API 5 冒烟适配器仍由旧模板渲染。
- 包：模块 ZIP 仍严格为 DLL + `module.json`，宿主标准包和更新器沙箱通过。

## 设计评审记录

### 第一轮：方向与职责

结论：通过。

- 页面结构从“宿主模板 + 模块数据”改为“模块页面 + 宿主壳”，与不同游戏需要完全不同界面的目标一致。
- 新协议没有页面枚举或 ID 命名约定，不会把未来页面重新锁进模板。
- 公共保存字段、状态和弹框仍由宿主提供，避免每个模块重复实现产品级基础设施。

### 第二轮：兼容、生命周期与安全

结论：通过，附带强制条件。

- 保留 API 2 到 5 路径，避免已安装第三方包立即失效。
- 页面必须有显式取消和释放顺序；注册表重载必须发生在页面释放之后。真实 WPF 页面验证表明 WPF 会保留类型缓存，因此 API 6 明确采用进程期独立加载上下文，不再把“可回收”作为虚假保证；源包删除和下次启动清理必须验证。
- 模块仍受构建指纹、包白名单、单 SDK、只读诊断和语义字段策略约束；拥有 UI 不等于获得新的系统权限。
- 当前官方页面可以先用代码构建，契约同时允许模块内部 XAML；必须用真实打包 DLL 验证页面来自模块程序集、页面 `Dispose()` 被调用、安装源包可删除，并接受影子上下文仅在进程退出时释放。

### 第三轮：版本、发布与可验证性

结论：通过。

- 发布版本、Host API、Schema 三类数字已经分开，不会因为 Host API 6 把主程序错误改成 `6.0.0`。
- 主程序和模块分别读取各自标签，独立递增；补位规则由脚本和测试共同执行，不能只写在文档里。
- 发布顺序固定为：全部本地验证 -> 源码提交/推送 -> 主程序 Release -> 模块 Release -> 远端资产复核 -> 模块目录单独提交。
- 若模块 UI 的真实加载、卸载或包内容任一验证失败，则停止发布，不以源码能编译代替完成证据。
