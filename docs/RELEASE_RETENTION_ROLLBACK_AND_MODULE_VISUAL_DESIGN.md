# 发布保留、手动回退与模块视觉契约设计

## 目标与不可变决定

本设计同时解决四件事：GitHub 资产保留上限、主程序与专属模块的手动回退、模块页面的统一视觉边界、以及发布资产无法从标签提交逐字节追溯的问题。

- 主程序与每个游戏专属模块分别最多保留 3 个正式 GitHub Release 包。
- 保留规则完全自动，不要求用户选择保留哪个版本或保留几个。
- 回退只能由用户主动点击触发；不得因为检查版本、启动失败、兼容性失败或服务器版本较低而自动降级。
- 主程序回退与模块回退使用一致的版本比较规则，但必须使用不同的安装流程和界面入口。
- 主程序与模块版本号独立递增，但每个正式版本必须通过显式兼容元数据建立对应关系。
- 模块决定页面结构、分组和交互；宿主决定主题颜色、字体、控件样式、间距基准和明暗主题切换。
- Last Epoch 资源页采用“顶部现有分类 + 单张资源表格”，不得使用资源主从列表，也不得增加“全部”分类。
- 正式资产必须从干净的已提交源码构建，二进制内嵌提交号必须等于发布标签指向的提交。

## 正式版本保留策略

### 识别与排序

- 主程序正式标签只匹配 `vA.B.C`。
- 模块正式标签只匹配 `{game}-vA.B.C`，并按游戏短名单独分组。
- `A.B.C` 使用十进制逐次发布规则；B、C 都只能为 0 到 9。排序必须解析数值，不得按字符串排序。
- 草稿、预发布、无预期 ZIP 或资产未完成的 Release 不计入可回退版本，也不由自动清理误删。

### 保留与删除

- 每组保留数固定为 3，不提供用户设置。
- 新 Release、资产 SHA-256、公开下载地址和版本目录全部验证成功后，才允许清理同组第 4 个及更旧的 Release。
- 清理删除 GitHub Release 及其资产以释放空间，但保留 Git 标签，继续保存源码历史和审计证据。
- 删除前必须再次确认仓库、标签前缀、Release ID、预期资产名和版本排序；不得用宽泛名称或全仓批量删除。
- 清理失败不回滚已经成功的发布；报告失败并允许幂等重试。不得为了满足数量上限而删除尚未完成验证的新 Release。

当前远端主程序和每个官方模块均只有 2 个正式 Release；本次发布后正好为 3，不会执行远端删除，但清理逻辑必须用模拟数据覆盖第 4、5 个版本。

## 主程序手动回退

### 发现规则

主程序仓库维护 Schema 1 的 `release-index.json`，保存服务器当前最多 3 个正式版本。每项包含版本、Host API 支持范围、模块目录 Schema 上限、下载地址、资产字节数、SHA-256 和源码提交号。该索引只在 Release 资产远端验证后单独提交，普通 GitHub Release API 只作为索引资产存在性复核来源，不能代替兼容元数据。

`ApplicationUpdateService` 读取发布索引，复核对应正式 Release，筛选出正确 Windows x64 资产，按版本从高到低排列。

- `updateTarget`：严格高于本地版本的最高服务器版本。
- `rollbackTarget`：严格低于本地版本的最高服务器版本。
- 版本相等只表示当前版本，不产生安装动作。
- 检查版本永不下载、安装或回退。

### 用户交互

- 保留现有“检查更新/更新”入口。
- 增加独立的“回退到 vX”按钮，仅在存在 `rollbackTarget` 时启用。
- 点击后明确显示本地版本、目标版本和“将关闭并重启主程序”，再次确认后才下载。
- 下载前使用目标主程序的 Host API 支持范围逐个检查本地已安装模块。任一模块不兼容时阻止主程序回退，列出模块名、本地模块版本及其要求，并提示用户先手动回退相应模块；不得自动替用户回退模块。
- 下载、HTTPS、文件名、大小和 SHA-256 校验与更新共用同一条安全链路。
- 待安装清单记录操作类型 `Update` 或 `Rollback`，但更新器使用相同的事务替换、锁重试和失败恢复机制。
- 更新器安装失败时恢复原文件属于事务失败恢复，不属于自动版本回退。

## 专属模块手动回退

### 目录 Schema

模块目录升级到 Schema 5。为兼容旧主程序，模块顶层继续保留当前最新版的 `version`、`hostApiVersion`、`compatibleBuilds`、`editors`、`downloadUrl` 和 `sha256`；新增 `releases` 数组保存从新到旧最多 3 个完整版本快照。

每个版本快照包含：

- `version`
- `hostApiVersion`
- `minimumHostVersion`
- `maximumHostVersion`（可空；有值时为包含边界）
- `compatibleBuilds`
- `editors`
- `downloadUrl`
- `sizeBytes`
- `sha256`

稳定的模块 ID、显示信息、进程名、贡献者和 legacy IDs 仍只保存在模块顶层。发布脚本从旧顶层条目和新资产自动维护 `releases`，不要求人工选择历史版本。

旧目录条目和旧包没有 `minimumHostVersion` 时，只能按已经发布并核验过的 Host API 引入版本迁移：本轮保留历史中的 API 4 映射为主程序 `0.4.1`，API 6 映射为 `0.4.3`；API 7 显式要求 `0.4.4`。无法从已发布事实确定的旧 Host API 不得猜测，相关版本不进入可安装/可回退候选，并给出元数据缺失诊断。

### 比较与入口

- 模块更新目标：与当前游戏构建、当前主程序版本及 Host API 兼容，且严格高于本地版本的最高服务器版本。
- 模块回退目标：与当前游戏构建、当前主程序版本及 Host API 兼容，且严格低于本地版本的最高服务器版本。
- “更新”和“回退到 vX”使用两个独立按钮；回退必须再次确认。
- 没有适用的更低版本时不显示可用回退动作。
- 不允许把另一个游戏的版本或只因版本号较低但构建不兼容的包作为回退目标。

## 主程序与模块版本对应关系

“版本独立”只表示编号不相等、不联动提升；兼容关系必须显式记录和验证。

- 主程序发布索引项声明 `minimumModuleHostApi`、`maximumModuleHostApi` 和 `maximumCatalogSchemaVersion`。
- 模块每个 release 快照声明 `hostApiVersion`、`minimumHostVersion` 和可选 `maximumHostVersion`。
- 模块包内 `module.json` 携带同样的主程序版本范围；宿主安装时同时核对目录与包内清单，防止目录被错误修改。
- 模块安装、更新、回退必须同时满足主程序版本范围、Host API 和游戏构建三层兼容性。
- 主程序回退必须确保目标主程序支持所有已安装模块；不兼容时阻止操作并要求用户先手动回退模块。
- 主程序升级继续兼容旧 Host API；如果未来确实移除旧 API，必须在该主程序发布索引中收紧 `minimumModuleHostApi`，不能隐式破坏。

本次对应关系：主程序 `0.4.4` 支持 Host API 2–7 和目录 Schema 5；三个新模块版本使用 Host API 7，最低主程序版本均为 `0.4.4`。旧模块版本保留其实际 Host API 和对应最低主程序版本，不伪造为 API 7。

### 安装生命周期

- 首次安装可在当前进程加载。
- 替换已安装模块时，先下载到版本隔离目录、验证包和清单，再原子更新 `installed.json`。
- Host API 6 及以上 WPF 模块不能保证进程内卸载。更新或回退成功后，当前模块立即停用，页面取消并释放，提示用户手动重启主程序后启用目标版本；不得在当前进程强行加载新旧两个 WPF 版本。
- 用户取消重启时保持主程序运行，但该模块保持停用状态。其他游戏模块不重载，避免重复积累非 collectible 上下文。
- 安装失败保持原登记版本和当前页面，不属于自动回退。

## 宿主视觉契约与模块布局自由

### 宿主拥有

- 主题调色板及动态切换。
- 字体族、字号层级、文字和禁用状态颜色。
- Button、TextBox、ComboBox、DataGrid、TabControl、ListBox 等通用控件样式。
- 页面背景、卡片、边框、危险操作和选择状态样式。
- 页面外壳与游戏内编辑器导航。

SDK 提供稳定的主题资源键和间距常量；宿主在模块 View 的父级注入并继承这些资源。模块必须使用 `DynamicResource`/SDK 键，不得写死颜色、替换全局资源字典、设置独立字体体系或创建自己的主题切换。该正式视觉契约属于 Host API 7，避免 Host API 6 主程序在缺少资源键时错误接受新模块。

官方模块验证增加视觉规则检查：拒绝硬编码颜色、模块级全局主题字典和自定义窗口外壳。运行时仍保留模块任意 WPF 布局能力；视觉约束是设计系统，不重新引入 `Kind` 页面模板。

### 模块拥有

- 页面结构、列数、分组、导航方式和控件组合。
- 领域专属的表格、卡片、滑块、标签和操作流程。
- 页面内的数据刷新、筛选、编辑和生命周期逻辑。

## Last Epoch 资源页

资源页不再使用通用 `EntityEditorPage` 的左侧实体列表和右侧字段表格，改为 Last Epoch 模块内的专属页面。

- 顶部分类直接取当前运行时已有 `AdapterEditorEntity.Summary` 分类，固定当前三项：`词缀碎片`、`符文与雕文`、`副本钥匙`。
- 不增加“全部”。默认选中第一个实际分类。
- 点击分类后，下方同一张 DataGrid 直接显示该分类的全部资源。
- 每行显示资源名称、当前数量、状态；未拥有资源显示 0。
- 修改和保存字段直接作用于当前表格选中行，不再要求先在左侧选择资源。
- 刷新后保留仍存在的分类、筛选文本和选中资源；分类缺失时回到第一个实际分类。
- 页面只使用宿主主题资源和标准控件样式。

## 发布溯源修复

正式顺序调整为：

1. 完成代码与文档，执行提交前的三轮实现审查。
2. 提交源码；确认工作树干净。
3. 从该干净提交重新构建全部最终 ZIP，不复用提交前产物。
4. 读取 EXE/DLL `ProductVersion`，确认 `+{SourceRevisionId}` 等于当前 `HEAD`。
5. 完整运行包启动、更新器、真实模块加载及目录验证。
6. 在同一提交创建 annotated tag，确认标签提交与二进制提交号一致。
7. 推送源码与标签，创建 Release，上传并复核远端 SHA-256。
8. 更新主程序发布索引、模块目录版本历史并分别单独提交；确认公开 raw 元数据可读。
9. 按组执行“保留最新 3 个”清理并复核，不删除标签。

发布脚本必须拒绝脏工作树、提交号不一致、同名资产内容不同、版本跳号、目录引用不存在的资产以及清理范围不明确的情况。

## 验证矩阵

### 版本与保留

- 0、1、2、3 个 Release 不删除；第 4 个只删除最旧 Release；每个模块短名独立计算。
- 标签保留；草稿、预发布、异常命名和其他仓库 Release 不受影响。
- 删除流程模拟、执行和幂等重试均有测试。

### 主程序回退

- 服务器高于、等于、低于和混合本地版本。
- 更新目标与回退目标同时存在时分别正确。
- 只有显式点击回退才创建 `Rollback` 待安装清单。
- SHA-256 失败、下载中断和更新器锁冲突不改变当前安装。
- 目标主程序不支持任一已安装模块时阻止回退，且不自动改变模块版本。

### 模块回退

- 每个模块最多 3 个版本记录且互不串线。
- 只选择兼容当前构建和当前 Host API 的最高较低版本。
- 目录版本范围、包内版本范围和当前主程序版本必须一致通过。
- API 6 及以上更新/回退后页面释放、模块停用、其他模块不重载，重启后加载目标版本。
- 失败时原 `installed.json` 和当前模块保持不变。

### 页面与主题

- Last Epoch 资源页只有三个现有分类且无“全部”。
- 分类切换直接改变单表格行集合，不出现左侧资源列表。
- 明、暗、护眼绿、暖沙、雾蓝五套主题动态切换后页面一致。
- 官方模块无硬编码颜色或自定义全局主题。

### 发布溯源

- 每个最终 EXE/DLL 的 `ProductVersion` 提交号等于标签提交。
- 最终 ZIP SHA-256 与远端资产一致。
- 从标签提交重建的程序集提交元数据一致；提交前旧产物不得进入 Release。

## 三轮设计审查记录

1. 方向审查：通过。版本号相互独立但兼容关系显式记录；主程序与模块分别手动回退；保留上限按组固定为 3；模块掌握页面结构、宿主管理视觉；Last Epoch 采用顶部三分类与单表格，无“全部”和左侧资源列表。
2. 兼容与生命周期审查：通过并补正。发布索引和模块快照增加资产字节数；明确旧 API 4/6 的已发布最低主程序映射和未知元数据拒绝策略；把不可进程内替换边界写为 Host API 6 及以上，替换后仅停用目标模块并要求手动重启。
3. 发布与可验证性审查：通过。版本递增为主程序 `0.4.4`、三个模块各自末位加一；最终资产只能从干净的标签提交重建；目录/索引公开验证成功后才能清理；当前每组由 2 个增加到 3 个，因此本次不会删除远端 Release，但 4/5 个版本的清理选择必须由测试证明。

## 三轮实现复核记录

1. 静态契约与状态复核：通过并修正两项。模块候选现在必须先命中当前游戏构建，不能只因主程序/API兼容就成为更新或回退目标；模块待重启状态改为累计状态，同时用本次替换的局部状态决定是否停用，避免另一个模块的首次安装被误判为替换。
2. 构建与自动验证复核：通过并修正验证包装层。主程序和更新器 Release 构建零警告；烟雾测试覆盖版本混合目标、显式 `Rollback` 清单、主程序兼容阻断、模块三层兼容、Schema 5 历史选择、Last Epoch 单表格页面结构和保留 0–5 个版本；PowerShell 子脚本改为依靠异常传播，避免把成功后的空 `$LASTEXITCODE` 误判成失败；PowerShell 语法、JSON Schema 和官方模块视觉规则全部通过。
3. 发布边界复核：通过。版本均为各自最新标签的唯一下一版；最终打包脚本强制干净工作树并核对 `ProductVersion == HEAD`；发布脚本要求带注释标签、分支和标签同提交、远端大小/SHA-256 一致；索引/目录只能复用已验证 ZIP，保留清理只能在公开元数据验证后执行。
