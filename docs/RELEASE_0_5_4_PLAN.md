1. 主程序、更新器、页面核验器与正式入口默认版本从 0.5.3 按计数规则递增为 0.5.4。Host API 8、SDK、资料 Schema 7、目录 Schema 5 均不变。
2. 游戏归属按实际原始名称及明确别名识别，用户可编辑的库备注不参加判断。公共启动器/浏览器的同名窗口不是游戏实例；普通小更新不因文件哈希改变被拒绝。宿主不增加任何游戏固定名称、App ID、地址或模块专用分支。模块 ID 仍只用于管理包及读取声明。
3. 维护工具默认预览，只考虑明确目录中的 ZIP。保护发布索引标准输入、模块目录保留输入和三份不同离线内容（最新完整包优先）；未知、无核验记录、未来版本、非 ZIP、目录、源码和个人数据保留。Apply 前重新核对方案与目标；不挂到打包/发布过程自动清理。
4. 完整 Release 构建及冒烟、清理工具隔离回归、发布基础设施/保留回归、离线组合回归与差异复核通过后提交源码。从干净提交构建正式标准 ZIP，验证真实启动及候选更新器恢复，标签指向其源码提交。

6. 使用正式标准包与现有四个模块制作简短名称的完整离线包，实际加载 DLL/14 个页面，独立启动与冻结记录核验。完整离线包只本地交付，不上传 GitHub。
7. 新产物和索引完成后重新计算真实目录预览，向用户提供每个删除候选、原因及保留范围。清单只是建议，未执行任何真实旧包删除；等待用户决定。

## 发布前方案三遍复核

- 第一遍（需求和方向）：实际游戏名称与备注分离，公共同名窗口排除，小更新仍认作同一游戏。通用宿主修复不会虚增模块版本或改变其业务规则。
- 第二遍（安全和依赖）：正式包/目录输入及最新完整离线内容受保护，旧核验脚本不再依赖固定离线别名。未知文件不猜删，默认不执行 Apply。索引三份与实体旧资产删除分离，尊重本次先预览的授权。
- 第三遍（来源和交付）：先验证/提交，再从干净源码构建；标签、ProductVersion 和资产散列一致。发布失败只恢复同一个上传步骤，不覆盖 0.5.3 资产；完整离线包本地交付。
