# v0.3.0-preview.13 模块卸载、应用更新与下载反馈修复方案

> 状态：方案已完成并通过两轮审查；实现、回归和本地打包已完成，等待用户测试。本轮不提交、不发布。

## 1. 问题与证据

### 1.1 专属模块卸载失败

用户卸载 WorldApart 模块时收到 `Access to the path 'GameValueEditor.Modules.WorldApart.dll' is denied.`。

当前 `GameAdapterRegistry` 直接从 `data/modules/packages/{module-id}/{version}` 加载 DLL。卸载时虽然调用可收集 `AssemblyLoadContext.Unload()` 和 GC，但 GC 发生在仍可能保留加载上下文或适配器引用的同一调用栈内；Windows 文件句柄未必已释放，紧接着删除正式包目录就会失败。失败后的注册表回滚还可能让游戏库模块标志、当前适配器和专属页内容暂时不一致。

### 1.2 应用更新遇到文件占用

本次没有保留下来的错误截图或 `update-error.log`，因此不能武断认定具体被占用的文件。但当前更新器确实存在可复现的薄弱点：只等待主进程退出，然后直接用 `File.Copy(..., overwrite: true)` 逐个覆盖正式文件；没有等待句柄释放、没有针对短暂占用重试，也没有替换事务和失败回滚。任一文件被退出尾声、杀毒软件、索引器或其他程序短暂占用，都可能留下部分文件已经更新、部分文件仍旧的混合状态。

更新器本身已经从 `data/updates` 下的副本运行，正常情况下不会覆盖正在执行的自己；本轮继续保留这个正确做法。

### 1.3 下载缺少进度和明确超时

模块和应用更新都以流方式复制到 `.download` 文件，但没有报告已传输字节。`HttpClient` 的 30 秒超时主要覆盖建立请求/取得响应头，后续流复制没有独立的无进度超时和总时限，界面会长期停留在“下载中”。

### 1.4 交互和发布边界

- “可更新”和“卸载”按钮距离过近，容易误点。
- 进程角色用于内部多进程自动路由，不应在进程下拉框中让用户看到“主进程/游戏数据”等角色提示。
- 完整离线包用于 QQ 群等国内分发，只需要本地生成、验证并报告路径和摘要，不应作为 GitHub Release 资产上传。

## 2. 实施方案

### 2.1 模块影子加载

1. `GameAdapterRegistry` 仍从正式包读取并校验 `module.json`，但把整个已验证模块目录复制到本次加载专用的运行时影子目录，再从影子目录加载程序集和依赖。
2. 运行时目录位于便携数据目录 `data/modules/runtime/{pid}-{session-id}/{load-id}`；每次重新加载使用新的 `load-id`，避免尚未完成回收的旧上下文阻塞新模块。
3. 正式包目录不再包含进程正在执行的 DLL，因此单独卸载、从库移出和同版本重装都不依赖 CLR 何时完成回收。
4. 注册表释放或重新加载后尽力清理本会话旧影子目录；下次启动只清理归属进程已不存在的陈旧会话目录，不触碰其他仍在运行的肝肾大圣实例。
5. 模块停用时仍先停止字段锁定、清空全部会话中的适配器引用，再更新 `installed.json`、重载注册表并删除正式包。
6. 影子复制跳过重解析点，并逐项校验源/目标均未逃出模块包和本次运行目录；多实例目录通过 PID 识别，宁可延后清理也不删除其他存活实例的运行文件。

### 2.2 卸载失败的最终兜底

1. 正式包删除采用短时异步重试，处理杀毒软件或索引器造成的瞬时占用，不阻塞 UI 线程。
2. 多次重试后仍无法删除时，不把模块重新注册为“已安装”；改为写入受路径校验保护的待清理记录。模块已停用、不会在重启时重新加载，游戏库状态保持一致。
3. 下次应用启动在构造适配器注册表之前重试待清理项；成功后移除记录，失败则保留供以后继续清理。
4. 如果同一模块仍有待清理文件且无法清除，重新安装时给出明确提示，要求重启肝肾大圣后再试，而不是产生第二份混乱状态。
5. 待清理记录只保存通过文件名片段校验的模块 ID，清理时重新计算仓库内路径；删除重试为异步流程，不在 UI 线程同步等待。

### 2.3 更新器事务与占用处理

1. 保持从 `data/updates` 中的更新器副本运行，并等待主进程退出。
2. 对主程序可执行文件增加独占打开探测，确认退出后的文件句柄已经释放。
3. 先把更新包内全部非 `data` 文件写入目标目录同盘的临时文件，完成后才开始切换正式文件。
4. 每个目标采用有限次数、递增等待的替换重试；错误信息包含具体目标路径和等待时长。
5. 替换前保存旧文件备份。任何一个文件最终替换失败时，按相反顺序恢复已经替换的文件，确保旧版本仍完整可运行；`data` 永不覆盖。
6. 成功后删除备份、待更新清单和安装包；失败时写入完整日志并重启原版本，不强制反复自动尝试同一失败包。
7. 原版本重启后只弹出一次主题一致的“更新未完成”提示，显示具体失败文件、错误摘要和日志路径；已展示状态单独记录，既保留诊断证据，也避免每次启动重复打扰。
8. 应用更新只接受精确的标准包命名 `GameValueEditor-v{version}-win-x64.zip`，明确排除 `complete-offline`，避免历史 Release 中的完整离线包被误选为在线更新包。

### 2.4 统一流式下载和界面反馈

新增宿主内部共用的流式下载组件，模块服务和应用更新服务均通过它下载：

- 校验 HTTPS、HTTP 状态、Content-Length、最终字节数和既有 SHA-256。
- 每次读取更新已下载字节，按节流后的频率向 UI 报告，避免每个网络块都触发界面刷新。
- 已知总长度时显示 `42% · 39.1 / 93.0 MB`；未知总长度时显示 `已下载 39.1 MB`。
- 连续 60 秒没有读到新数据时抛出中文超时错误；总下载时间超过 20 分钟时终止。
- 用户取消、超时、网络失败或校验失败时删除临时文件，按钮和状态恢复为可重试。
- 模块下载进度显示在“本游专属”状态区；应用更新百分比显示在右下角，详细字节信息同步显示在左下角状态栏。
- 调用方取消、20 分钟总时限和连续 60 秒无数据是三个独立的终止原因；进度通过捕获 UI 同步上下文的 `IProgress` 节流上报，不允许后台线程直接修改绑定属性。

### 2.5 界面和进程显示

- 给“可下载/可更新”按钮增加右侧间距，使其视觉上靠近“检查新有”，并与“卸载”明显分开。
- `ProcessItem.DisplayName` 只保留窗口标题、进程名和 PID；内部 `GameProcessRole`、多进程分组和数据进程选择逻辑不变。

### 2.6 完整离线包政策

- 更新发布 skill 和项目文档：完整离线包只在本地构建与验证，报告路径、SHA-256 和内置模块版本，供用户自行上传 QQ 群。
- 主程序标准包和独立模块包仍按原规则发布 GitHub。
- 不自动删除已经上传的历史完整离线包；删除远端资产必须由用户另行明确授权。

## 3. 验收与回归测试

1. 模块从影子目录加载时，保持注册表和游戏连接仍存活也能删除正式包 DLL；卸载后界面、游戏库标志和 `installed.json` 一致。
2. 模块删除遇到模拟瞬时锁时会等待并成功；遇到持续失败时记录待清理项且不会重新加载，重启后可清理。
3. 从库移出仍保持游戏进程的临时连接和通用扫描，专属能力立即停用。
4. 更新器面对短暂锁定的目标文件会等待后成功；面对持续锁定会回滚，旧程序和 `data` 内容保持不变。
5. 更新失败后的旧版本只提示一次准确错误；存在标准包与完整离线包的历史 Release 时始终选择标准包。
6. 已知和未知 Content-Length 的下载进度均正确、单调；模拟连续无数据会在测试用短时限内超时并清理临时文件。
7. 进程列表不再出现角色后缀；内部多进程选择测试继续通过。
8. 浅色、深色及其他主题渲染中，“可更新”和“卸载”有清楚间距。
9. Release 构建、宿主冒烟、原生倍速、更新器沙箱、本地标准包启动和本地完整离线包启动通过。
10. 生成 `v0.3.0-preview.13` 本地测试 ZIP，报告位置与 SHA-256；不提交、不打标签、不上传 GitHub。

## 4. 发布约束

本轮未经用户测试确认不得提交或发布。用户确认后，正式发布仍遵循模块先发布并验证、再更新在线目录、最后发布主程序标准包的顺序；完整离线包始终只保留在本地供 QQ 群分发。

## 5. 两轮方案审查记录

### 第一轮：用户流程与失败恢复

1. 发现历史 GitHub Release 同时存在标准包和完整离线包时，原有宽松名称匹配可能误选完整包；方案补充精确标准包匹配和完整包排除规则。
2. 发现更新失败虽然写日志，但原版本重新启动后没有可靠的人类可见反馈；方案补充一次性主题弹框、具体文件和日志路径。
3. 逐项核对首次安装、模块更新、单独卸载、从库移出、下载超时、更新成功、更新失败回滚和下次启动清理，状态均有可恢复出口。

结论：用户流程通过，但必须加入精确资产选择和一次性更新错误反馈后才能实施。

### 第二轮：线程、文件系统与安全边界

1. 影子目录必须兼容多个肝肾大圣实例，清理时依据 PID 跳过存活实例；模块复制跳过重解析点并保持仓库路径边界。
2. 待清理记录不得保存任意绝对路径，只保存安全模块 ID；模块服务必须在适配器注册表之前创建并完成启动清理。
3. 删除等待改为异步；更新临时文件和备份位于目标同卷，区分原有文件与新增文件，才能可靠回滚。
4. 下载总时限、无进度时限和用户取消必须分别报告；进度上报必须经过 UI 同步上下文且节流。
5. 核对修复没有绕过 HTTPS、包路径、SHA-256、`data` 保护或精确发布包命名，也不扩大远端删除权限。

结论：第二轮通过。方案可以实施，不需要引入复杂 DI 框架或大规模重写现有 MVVM。
