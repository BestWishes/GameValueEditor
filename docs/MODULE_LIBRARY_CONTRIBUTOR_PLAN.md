# 游戏专属模块管理、游戏库与贡献者实施方案

> 状态：已通过两轮方案审查，功能实现与本地验证已完成；目标发行版本为主程序 `v0.3.0-preview.12`、`game.fzzml` v2.0.1、`game.worldapart` v1.0.1。适用于主程序与 `GameValueEditor-Modules` 模块中心的配套改造。

## 1. 已确认的产品规则

1. 游戏专属模块必须依附于一个正常的游戏库条目存在，不设计虚拟条目或独立模块管理页。
2. 已连接但尚未入库的游戏可以点击“检查新有”。下载安装专属模块成功后，主程序使用服务器清单中的正式游戏名称自动把游戏加入游戏库，并保存当前精确构建指纹。
3. 一个游戏库条目最多关联一个稳定游戏模块 ID；同一模块 ID 不得生成重复游戏条目。
4. “从库移出”同时移除游戏的全部版本、快捷入口和本地专属模块。若游戏仍连接，则保留临时连接和通用扫描，解除专属模块能力。
5. “卸载”只卸载本地专属模块，保留游戏库、版本和快捷入口；重新安装后快捷入口可以恢复使用。
6. 完整离线包或历史安装中已有模块但缺少游戏库条目时，应用启动时按同一规则补建正常游戏库条目，确保不存在无法管理的模块文件。
7. 游戏库条目显示本地模块标志，并支持按连接状态、名称、本地模块状态排序。
8. 贡献者按整个游戏专属模块汇总，不区分具体游戏内编辑模块，不显示贡献次数、代码量、排名、角色或贡献内容。
9. “贡献者”使用普通按钮，位于“卸载”右侧并留出明显间距。弹框显示 GitHub 名称、首次贡献日期、最新贡献日期；名称链接到 GitHub 主页，支持按三列排序。
10. 贡献者数据由模块中心的可信自动化根据成功合并的 PR 生成，贡献者不能在投稿中手工维护名单。

## 2. 主程序状态模型

### 2.1 游戏库

`GameProfile` 增加持久化的 `ModuleId`，并增加不序列化的 `IsModuleInstalled`、模块标志显示属性。应用启动时读取已安装模块清单并完成：

- 按 `ModuleId` 关联既有条目。
- 为旧版本数据按进程名与精确构建指纹补齐唯一可确认的 `ModuleId`。
- 为没有条目的已安装模块创建普通 `GameProfile`，名称和进程名来自经过校验的本地模块清单；未连接时允许版本数为零。
- 对重复或无法唯一匹配的旧条目不自动合并用户数据，而是为模块创建一个新的、带稳定 `ModuleId` 的普通游戏库条目。旧包缺少正式游戏名时依次使用包内显示名和模块 ID 作为安全回退；缺少进程名时保持为空，确保模块始终可管理，但不猜测连接目标。

排序模式：

- `连接状态`：连接中优先，其后按置顶、最近使用、名称。
- `游戏名称`：置顶优先，其后按名称。
- `本地专属模块`：已安装模块优先，其后按置顶、名称。

### 2.2 未入库连接目标

模块检查目标不再依赖 `SelectedGame + SelectedVersion`。新增只读目标模型，来源可以是：

- 当前连接进程及实时生成的 `VersionFingerprint`。
- 已入库游戏的所选历史版本。

未入库连接在版本指纹完成后即可检查服务器清单、识别本地模块并安装；保存快捷入口仍要求正式入库。

### 2.3 模块生命周期

扩展现有 `GameModuleCatalogService` 为模块生命周期服务，负责：

- 在线清单检查和兼容模块选择。
- 已安装模块、清单和贡献者读取。
- 下载、哈希校验、安全解压和原子安装。
- 从已安装清单停用模块并清理包目录；删除失败时回滚安装记录并重新加载模块，确保管理入口不会消失。
- 为游戏库提供模块 ID、正式游戏名、进程名、兼容构建和贡献者快照。

`MainViewModel` 只负责把当前连接/选择转换成模块目标，并协调游戏库、会话与界面状态。模块安装与卸载后统一刷新适配器注册表和所有会话。

不引入 DI 框架。新增一个简单的应用组合根统一创建 `ProfileStore`、进程/指纹/扫描/倍速服务、模块管理服务、适配器注册表和应用更新服务，再通过构造函数传给 `MainViewModel`。把嵌套的游戏连接会话状态移到独立模型，并集中封装“适配器状态发生变化”的属性通知，避免安装、卸载、连接和清空路径继续复制同一组通知代码。

卸载正在使用的模块时：

1. 阻止新的专属操作并停止该模块字段的锁定维护。
2. 从所有会话清除该模块适配器和专属列表，但保留进程连接、倍速与通用扫描。
3. 从 `installed.json` 原子移除模块，使重启后绝不再加载。
4. 卸载可收集加载上下文并删除包目录；若 Windows 暂时锁定 DLL，则恢复安装记录和适配器并报告失败，不留下无法管理的僵尸目录。
5. 刷新游戏库模块标志、排序和本游专属状态。

“从库移出”采用先停用/卸载模块、成功后再删除游戏库条目的顺序。模块停用失败时保留游戏库条目并报告错误，不制造无法管理的残留模块；模块已经从 `installed.json` 停用但库保存失败时，下次启动按实际安装状态修复标志，用户仍可再次操作。

## 3. 模块元数据

模块中心的源码 `games/{slug}/module.json` 是游戏身份、兼容构建和编辑器元数据的唯一事实来源。服务器 `catalog.json` 的对应字段由发布脚本从源码清单生成并校验，不允许人工维护两份不同内容。源码清单增加：

- `gameDisplayName`：自动入库时使用的正式游戏名称。
- `processNames`：离线包首次启动和寻找运行进程所需的进程名。
- `compatibleBuilds`：精确构建指纹，不允许通配符。
- 贡献者不由源码清单手写；发布脚本读取 `contributors.generated.json`，只在发行包内的 `module.json` 和服务器 `catalog.json` 写入自动生成快照。

贡献者记录：

```json
{
  "githubId": 1,
  "githubLogin": "octocat",
  "displayName": "The Octocat",
  "profileUrl": "https://github.com/octocat",
  "firstContributionDate": "2026-09-29",
  "latestContributionDate": "2026-09-29"
}
```

`githubId` 是稳定身份；界面显示 GitHub 公共资料的 `displayName`，为空时退回 `githubLogin`。主程序只允许打开 `https://github.com/{githubLogin}` 形式的链接。

## 4. 贡献者自动生成

模块中心每个游戏目录保存 `contributors.generated.json`。该文件由自动化维护，PR 不允许直接修改。

可信 `pull_request_target` 工作流只在 PR 已合并到 `main` 后：

1. 查询合并提交关联的 PR 和修改文件。
2. 根据 `games/{slug}/...` 确定受影响的游戏模块；仅修改生成文件、仓库级文档或无关路径不计入模块贡献。
3. 读取 PR 作者的 GitHub 数字 ID、登录名、公共名称和主页。
4. 使用 PR 的 `merged_at` 作为服务器可信日期；首次记录最小日期，最新记录最大日期。
5. 一个 PR 修改多个游戏时进入多个游戏的贡献者名单；Bot 和未合并 PR 不记录。
6. 自动提交生成文件。发布脚本把贡献者快照写入发行包 `module.json` 和 `catalog.json`。

历史已有模块使用仓库所有者的 GitHub 身份和各模块目录的首次/最新可信提交日期进行一次受控初始化，之后完全由合并工作流更新。另设低频计划任务刷新所有已有贡献者的 GitHub 公共名称和主页，身份始终以数字用户 ID 为准，名称变化不会生成重复记录。

## 5. 自动审核

模块中心增加两层 PR 检查：

1. 普通 `pull_request` 工作流在 GitHub 托管的临时环境中以只读令牌构建和测试投稿代码，不读取发布密钥，不产生发布物。
2. 可信策略检查使用默认分支中的审核规则，只把 PR 文件和元数据当作数据分析，不执行投稿者提供的脚本；`.github/**`、发布脚本、Schema 和审核规则本身受 CODEOWNERS/分支规则保护，修改这些文件必须人工批准。

检查内容包括：

- 确认游戏目录、稳定模块 ID、编辑器 ID 和版本唯一。
- 校验源码清单、JSON Schema、Host API、进程名和全部精确构建指纹。
- 拒绝 PR 手工修改 `contributors.generated.json`。
- 构建完整模块解决方案并运行模块验证脚本。
- 检查下载地址、SHA-256 格式、包内路径、依赖和敏感信息。
- 生成“影响的游戏模块、元数据变化、构建与安全检查”摘要。

PR 工作流不持有仓库写权限和发布密钥。合并后的 `push` 可信工作流才查询关联 PR、更新贡献者文件；它不会签出或执行未合并分支代码。正式 Release 仍从可信主分支构建。未知游戏构建和真实写入效果不能仅靠 CI 判定，必须保留实机验证证据与一次人工安全确认。

## 6. 界面改动

- 右下角去掉更新操作两侧括号，当前版本与更新状态之间使用布局间距表达两个空格。
- 游戏库搜索框下方增加“排序”下拉框。
- 游戏库条目在连接标志前显示低干扰的本地模块标志。
- 本游专属顶部按钮顺序为“检查新有”“可下载/可更新”“卸载”，随后留出较大间距再显示“贡献者”。
- 下载按钮根据状态显示“可下载”或“可更新”；没有可执行操作时禁用。
- 卸载按钮仅在当前游戏有关联的已安装模块时启用。
- 贡献者按钮在本地或远程元数据存在贡献者时启用。
- 贡献者弹框使用可滚动、虚拟化表格，默认按名称排序，列标题或排序框可切换名称、首次日期、最新日期；不显示头像、贡献数量和内容详情。

## 7. 文档与兼容迁移

- 更新游戏模块与编辑模块设计文档、扩展指南、README 和实现进度。
- 模块中心更新 README、扩展规范、JSON Schema、模板模块和发布说明。
- 旧 `installed.json` 与旧模块包继续可读；缺少新元数据时优先从在线清单补齐，离线时也必须用包内显示名或模块 ID 创建可管理条目，只是不猜测进程和构建兼容性。
- 提升主程序预览版本；仅在模块发行包字节发生变化时分别提升对应模块版本。

## 8. 验收矩阵

- 未入库运行游戏可以检查模块；没有兼容模块时不自动入库。
- 未入库游戏下载安装成功后只生成一个正常游戏库条目，保存当前版本和模块 ID。
- 应用重启后模块、游戏库关联和本地模块标志保持正确。
- 从库移出会卸载模块；当前连接保留为无专属模块的临时连接。
- 单独卸载模块保留游戏库与快捷入口；重新安装后语义字段可恢复。
- 完整离线包首次启动会为每个内置模块创建可管理的游戏库条目。
- 三种排序与搜索组合正确，已连接游戏切换状态后实时重排。
- 贡献者名称链接、三种排序、大量条目滚动和深浅主题正确。
- 未受信任贡献者无法通过 PR 修改生成名单或获得发布权限。
- 旧游戏库、旧 `installed.json`、fzzml 与 WorldApart 现有编辑能力无回归。
- 主程序构建、冒烟、更新器沙箱、标准包启动和完整离线包启动通过。
- 变更模块构建、清单校验、包内容、在线下载、SHA-256 与错误构建拒绝通过。

## 9. 发布顺序

1. 完成模块中心元数据、贡献者生成、PR验证和文档，构建变更模块。
2. 发布不可变模块 ZIP 并验证线上哈希。
3. 更新并发布在线 `catalog.json`。
4. 完成主程序实现、迁移、测试和文档，发布新的主程序预览版。
5. 使用已发布主程序和模块清单制作完整离线包，验证首次启动自动入库与模块可管理性。

## 10. 方案审查记录

### 第一轮：用户流程与持久状态一致性

发现并修正：

1. 初稿对缺少新元数据的旧模块只计划显示错误，仍可能没有管理入口；现改为任何 `installed.json` 记录都必须生成正常游戏库条目，信息不足时使用显示名或模块 ID 安全回退。
2. 初稿未规定“从库移出”过程中卸载失败的事务顺序；现规定先停用/卸载模块，成功后才删除游戏库条目，失败时保留可操作入口。
3. 初稿只在新贡献合并时刷新 GitHub 名称；现增加低频刷新，数字 ID 保持身份稳定，显示名可跟随 GitHub 公共资料更新。
4. 核对了首次安装、更新、单独卸载、从库移出、仍在连接、应用重启、完整离线包、旧包迁移和保存失败等路径；均能回到“每个已安装模块有且只有一个带 `ModuleId` 的正常游戏库条目”的状态。

结论：产品流程通过第一轮审查，可以进入架构与安全审查；第二轮通过前仍不得开始功能代码实现。

### 第二轮：架构、安全与发布一致性

发现并修正：

1. 初稿允许源码 `module.json` 与 `catalog.json` 双份人工维护身份和兼容数据，容易漂移；现改为源码清单唯一，发布脚本生成并验证在线清单。
2. 初稿未防止投稿者在同一 PR 中修改审核脚本来绕过检查；现把无密钥构建测试与可信策略检查分层，并要求保护工作流、Schema 和发布脚本。
3. 初稿只说明从 `MainViewModel` 提取模块服务，仍可能继续在构造函数直接创建依赖和复制适配器通知；现加入轻量组合根、构造注入、独立会话状态和集中通知，不引入复杂 DI 框架。
4. 核对了卸载顺序：先清除所有会话对目标适配器的强引用，再从安装清单停用，再卸载注册表上下文，最后删除或登记待删除包目录，避免 Windows DLL 锁和下次启动重新加载。
5. 核对了供应链边界：投稿代码只在无密钥、只读、临时环境运行；贡献者自动化只在可信主分支运行；模块正式包必须从可信主分支构建并校验不可变 SHA-256。
6. 核对了版本和发布顺序：新字段对旧主程序保持 JSON 向后兼容；字节发生变化的模块独立升版；在线模块发布并验证后才更新清单，最后发布主程序和完整离线包。

结论：第二轮通过。方案在不引入新管理页面、复杂 DI 或大规模 MVVM 重写的前提下，能够安全承载本次功能；可以开始实现。
